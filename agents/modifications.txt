## 1. Passer Node 20 → Node 22

### Constat

Deux occurrences de `node:20-bookworm-slim` dans le Dockerfile (lignes 3 et 13). Le log montre :

```
npm warn EBADENGINE Unsupported engine {
  package: 'camera-controls@3.1.2',
  required: { node: '>=22.0.0' },
  current: { node: 'v20.20.2' }
}
```

GitHub Actions force déjà Node 24 pour ses propres actions (message répété 8× dans le log). La CI `ci_cd.yml` utilise aussi `setup-node@v4` avec `node-version: "20"`.

### Répercussions

| Correctif | Impact |
|---|---|
| Remplacer `node:20-bookworm-slim` → `node:22-bookworm-slim` | Résout le warning EBADENGINE. Compatibilité garantie avec `camera-controls@3.1.2`. Next.js 16.1.5 supporte Node 22. |
| Remplacer → `node:24-bookworm-slim` | Aligné avec l'environnement GitHub Actions. Plus récent, mais vérifier que toutes les dépendances npm supportent Node 24. Risque faible. |
| Dans `ci_cd.yml`, passer `node-version: "22"` | Cohérence entre CI et Docker. |

**Recommandation** : Node 22 (LTS actuel, plus stable que Node 24 en production). Node 24 n'est pas encore LTS et bien que GitHub Actions l'utilise, Next.js 16.1.5 est officiellement testé sur Node 22. Le log montre que `camera-controls@3.1.2` demande `>=22.0.0` — Node 22 suffit.

### Aucun changement de code applicatif nécessaire
Next.js, React, Three.js et toutes les dépendances actuelles (`next.config.ts`, `package.json`) restent identiques. Le changement se limite aux lignes 3 et 13 du Dockerfile + la version dans `ci_cd.yml`.

## 2. Traiter les vulnérabilités npm proprement

### Constat

Log : `16 vulnerabilities (1 low, 6 moderate, 8 high, 1 critical)`

La CI ne bloque pas sur les vulnérabilités. Le Dockerfile fait un `npm ci` silencieux.

### Répercussions

Un `npm audit fix --force` est dangereux : il peut casser Next.js 16.1.5, Three.js, React 19.2.3, etc. en forçant des mises à jour majeures non testées.

**Procédure recommandée (hors audit, action manuelle)** :

```bash
cd frontend
npm audit --omit=dev          # vulnérabilités runtime uniquement
npm audit fix --production    # correctifs safe runtime seulement
```

Puis ajouter dans le Dockerfile **après** `npm ci` :

```dockerfile
RUN npm audit --omit=dev --audit-level=high || exit 1
```

Cela bloque le build si une vulnérabilité runtime **high** ou **critical** persiste.

**⚠️ Attention** : certaines vulnérabilités peuvent être dans des dépendances transitives de Next.js lui-même. Si `npm audit fix --production` ne résout pas tout, il faudra soit :
- Surcharger la version dans `package.json` via `overrides` (ou `resolutions` si yarn)
- Accepter le risque si la vulnérabilité n'est pas exploitable dans le contexte de l'app
- Attendre un correctif amont

**Ce correctif n'affecte pas le code applicatif** (sauf si `overrides` sont ajoutés dans `package.json`).
