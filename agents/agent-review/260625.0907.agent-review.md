## Architecture du pipeline

```
[Fichier GPX/FIT]
     │
     ▼
[storage.load_dataframe(activity_id)]
     │
     ▼
[compute_derived_series(df)] → grade_series, moving_mask
[compute_summary_stats(df)] → avg_pace → cap = avg_pace * 1.4

     │
     ▼
```

## Fonctionnement détaillé du graphique

### 1. Source des données

Le graphique se base sur les données brutes d'une activité (DataFrame pandas chargé depuis un fichier GPX ou FIT). Les colonnes minimales requises sont :

| Colonne | Unité | Rôle |
|---|---|---|
| `distance_m` | mètres | Distance cumulée depuis le départ |
| `elevation` | mètres | Altitude à chaque point |
| `delta_time_s` | secondes | Écart temporel entre deux points consécutifs |
| `delta_distance_m` | mètres | Écart de distance entre deux points consécutifs |
| `speed_m_s` | m/s | Vitesse instantanée |
| `pace_s_per_km` | s/km | Allure instantanée |

Toutes ces colonnes sont produites par le pipeline de chargement (`storage.load_dataframe()`), qui découpe le fichier GPX/FIT en points avec un pas de temps d'environ 1 seconde.

---

### 2. Calcul de la pente (`grade_series`)

**Fonction** : `compute_grade_percent_series()` → `_compute_grade_percent()` dans `real_run_analysis.py`

La pente est calculée point par point avec la formule :

```
grade_% = (elevation[i] - elevation[i-1]) / delta_distance_m[i] × 100
```

Un **lissage** est appliqué avant le calcul :
- L'altitude est lissée par une **moyenne glissante centrée** sur une fenêtre de `DEFAULT_GRADE_SMOOTH_WINDOW = 5` points (soit ~5 secondes).
- Ce lissage réduit le bruit GPS sans déformer le relief réel.

Un **filtrage** est ensuite appliqué :
- Les segments où `delta_distance_m < MIN_GRADE_DISTANCE_M = 1.0m` sont exclus (pente non fiable sur des déplacements trop courts).
- Les valeurs infinies ou NaN sont remplacées par NaN.

La série de pentes est **continue** (une valeur par point), comprise entre environ -20% et +20% (clippée dans l'étape de binning).

---

### 3. Détection des pauses (`moving_mask`)

**Fonction** : `compute_moving_mask()` dans `real_run_analysis.py`

Le masque de mouvement filtre les arrêts pour ne pas fausser les statistiques d'allure :

1. La vitesse instantanée est lissée par une **médiane glissante** sur 3 points (supprime les à-coups GPS).
2. Un point est considéré comme "arrêté" si sa vitesse lissée reste sous `MOVING_SPEED_THRESHOLD_M_S` (seuil de marche lente).
3. Une séquence d'arrêt doit durer au moins `DEFAULT_MIN_PAUSE_DURATION_S = 5s` pour être comptée comme pause.
4. Le premier point après une pause est aussi marqué comme non-mouvant (comportement historique).

Résultat : un masque booléen `True = en mouvement`, de même longueur que le DataFrame.

---

### 4. Série d'allure utilisée (`pace_series`)

**Fonction** : `compute_pace_series()` dans `real_run_analysis.py`

L'endpoint `/pace-vs-grade` utilise les paramètres par défaut de `RealRunViewParams()` :

| Paramètre | Valeur | Effet |
|---|---|---|
| `pace_mode` | `"real_time"` | Allure instantanée par point (`df["pace_s_per_km"]`) |
| `smoothing_points` | `0` | Aucun lissage supplémentaire |
| `cap_min_per_km` | `avg_pace_min/km × 1.4` | Plafonne l'allure à 1.4× la moyenne (évite les valeurs aberrantes de marche/arrêt) |

Le cap est calculé dynamiquement : si l'allure moyenne de la sortie est de 5:00/km, le cap est à 7:00/km (420 s/km). Les points au-dessus sont écrêtés.

---

### 5. Binning et agrégation (`compute_pace_vs_grade_data`)

**Fonction** : `compute_pace_vs_grade_data()` dans `real_run_analysis.py`

C'est le cœur du calcul. Le pipeline complet :

#### 5.1 Filtrage
```
Données brutes (N points)
  → moving_mask & delta_time_s > 0  →  Points en mouvement uniquement
  → dropna(grade, pace, weight)      →  Suppression des valeurs manquantes
  → pace > 0 & weight > 0            →  Suppression des valeurs nulles
```

#### 5.2 Discrétisation
Les pentes sont réparties dans des **bins fixes de 0.5%** :
```
Bins : [-20.0, -19.5, -19.0, ..., -0.5, 0.0, +0.5, ..., +19.5, +20.0]
```
Soit 80 bins au total (40 négatifs, 1 zéro, 39 positifs). Le `pd.cut` avec `include_lowest=True` garantit que -20.0 et +20.0 sont inclus.

#### 5.3 Statistiques par bin
Pour chaque bin, les métriques sont calculées avec **pondération temporelle** (`weight_s = delta_time_s`) :

| Métrique | Calcul | Signification |
|---|---|---|
| `time_s_bin` | `sum(weight_s)` | Temps total passé dans ce bin |
| `pace_q50_w` | Médiane pondérée (quantile 0.5) | Allure "typique" dans ce bin |
| `pace_q25_w` | Quantile pondéré 0.25 | Allure rapide du bin |
| `pace_q75_w` | Quantile pondéré 0.75 | Allure lente du bin |
| `pace_mean_w` | Moyenne pondérée | Allure moyenne du bin |
| `pace_std_w` | Écart-type pondéré | Dispersion de l'allure dans le bin |
| `pace_n` | Nombre de points bruts | Taille d'échantillon |
| `pace_n_eff` | Taille d'échantillon effective | Pondérée par les poids (formule de Kish) |
| `grade_center` | Médiane pondérée des grades dans le bin | Centre "réel" du bin (≠ milieu théorique) |

Le `grade_center` est calculé comme la **médiane pondérée des pentes réelles** dans le bin, et non comme le centre fixe du bin. Cela évite les artefacts : si un bin [-2.0, -1.5] contient surtout des points à -1.9%, le centre sera ~-1.9% plutôt que -1.75%.

#### 5.4 Winsorisation (clipping des outliers)

Pour chaque bin ayant suffisamment de données (`time_s_bin ≥ 30s` et `pace_n_eff ≥ 8`) :
1. Calcul des bornes IQR : `[Q25 - 2×IQR, Q75 + 2×IQR]`
2. Si l'IQR est nul (données plates), fallback MAD : `[médiane ± 4×1.4826×MAD]`
3. Les valeurs hors bornes sont écrêtées aux bornes
4. `outlier_clip_frac` = fraction du temps écrêté

La winsorisation protège contre les artefacts GPS ponctuels (ex: un pic de vitesse à 2:00/km dû à une erreur de coordonnée) sans supprimer le point.

#### 5.5 Filtrage de qualité

Les bins sont filtrés a posteriori :
- `time_s_bin ≥ 20s` : au moins 20 secondes passées dans ce bin
- `pace_n_eff ≥ 5` : au moins 5 points effectifs

Les bins ne passant pas ces seuils sont **supprimés** de la sortie. Cela évite d'afficher des bins avec 2 secondes de données (non représentatifs).

#### 5.6 Champ backward-compat

`pace_med_s_per_km` est rempli avec `pace_q50_w` (médiane pondérée) si disponible, sinon avec la médiane non pondérée. `pace_std_s_per_km` utilise l'écart-type non pondéré (non filtré par les poids temporels).

### 6. Référence pro (`pro_pace_vs_grade.csv`)

**Fichier** : `backend/core/resources/pro_pace_vs_grade.csv`

Table de 27 points (de -10% à +15%) représentant l'allure d'un coureur élite (Kilian Jornet) en fonction de la pente. Exemples :

| Pente | Allure pro |
|---|---|
| -5% | 207.9 s/km (3:28/km) — allure optimale en descente |
| 0% | 220.0 s/km (3:40/km) — allure sur le plat |
| +5% | 278.2 s/km (4:38/km) |
| +10% | 330.0 s/km (5:30/km) |
| +15% | 407.6 s/km (6:48/km) |

Caractéristique notable : la courbe présente une **forme en U asymétrique** autour de 0%. L'allure la plus rapide est à -5% (207.9 s/km), puis ralentit des deux côtés — physiologiquement correct car au-delà de ~6% de descente, le coureur doit freiner.

Pour chaque bin, la valeur pro correspondante est obtenue par **interpolation linéaire** (`_interp_pro_pace_s_per_km`) entre les points du CSV. Hors plage [-10%, +15%], la valeur est étendue par la valeur au bord le plus proche.

### 8. Rendu frontend (Recharts)

**Composant** : `AllureVsPenteChart` dans `AllureVsPenteChart.tsx`

**Fetching** : React Query via `usePaceVsGrade(activityId)` avec `staleTime: 10min`.

**Mapping des données** :
```
API bin → BinPoint (frontend) :
  grade_center        → grade
  pace_med_s_per_km   → paceMean    (⚠️ en réalité la médiane, pas la moyenne)
  pace_std_s_per_km   → paceStd
  pace_n              → n
  pro_pace_s_per_km   → proPace
```

**Tri** : Les bins sont triés par `grade` croissant (des pentes négatives aux positives).

**Domaine X** : Symétrique autour de 0, calculé comme `min(20, max(|min_grade|, |max_grade|))`. Exemple : si les pentes vont de -8% à +12%, le domaine sera `[-12, +12]`.

**Ticks X** : Pas de 2.5%, symétriques autour de 0 (ex: -10, -7.5, -5, -2.5, 0, 2.5, 5, 7.5, 10).

**Domaine Y** : Calculé automatiquement à partir de toutes les valeurs visibles (paceMean ± paceStd + proPace), avec un padding de 4% de l'étendue.

**Éléments graphiques** (de l'arrière vers l'avant) :

| Élément | Type Recharts | DataKey | Rendu |
|---|---|---|---|
| Grille | `CartesianGrid` | — | Pointillés gris |
| Bande variabilité | `Area` (isRange) | `paceRange` = [paceMean-paceStd, paceMean+paceStd] | Remplissage gris 22% opacité |
| Courbe pro | `Line` | `proPace` | Pointillés gris (#64748b), épaisseur 1 |
| Courbe utilisateur | `Line` | `paceMean` | Plein noir (#0f172a), épaisseur 2 |
| Points | `Scatter` | `paceMean` | Cercles r=2, noir |

**Tooltip** : Affiche pour un bin survolé :
- "Mon allure: X:XX /km" (valeur de `paceMean`)
- "Pente: X.X%" (valeur de `grade`)
- "Allure pro: X:XX /km" (ou "—" si absent)

**États** :
- `isLoading` → "Chargement..."
- `error` → "Erreur de chargement."
- Aucun bin ou domaineAbs = 0 → `null` (composant invisible)

**Emplacement dans la page** : Le composant est rendu par `MetricsRegistryRenderer` dans la section "climbs", qui n'est visible que dans l'onglet **Climbs** (`activeTab === 'climbs'`). Il n'apparaît pas dans les onglets Charts, Aperçu, ou Détails.

## Problèmes classés

### 🔴 Bloquants

Aucun constaté.

### 🟠 Majeurs

#### M-1 : Mélange stats pondérées/non pondérées dans la bande de variabilité

- **Fichier** : `AllureVsPenteChart.tsx` l.71-73, 101-109 + `real_run_analysis.py` l.770-772
- **Problème** : Le centre = médiane pondérée (`q50_w`), l'écart-type = non pondéré (`std`). Le backend fournit `pace_std_w_s_per_km` (écart-type pondéré) mais le frontend l'ignore.
- **Impact** : Bande de variabilité trompeuse pour les distributions avec poids temporels hétérogènes.
- **Correction** : Utiliser `b.pace_std_w_s_per_km` pour la bande.

#### M-2 : Graphique uniquement visible dans l'onglet "Climbs"

- **Fichier** : `MetricsRegistryRenderer.tsx` l.129, `page.tsx` l.653-657
- **Problème** : `AllureVsPenteChart` est uniquement rendu dans la section climbs → onglet Climbs. Absent de l'onglet Charts.
- **Impact** : Découvrabilité réduite, l'utilisateur ne trouve pas le graphique.
- **Correction** : Ajouter dans l'onglet Charts.

#### M-3 : Le frontend ignore le tableau `pro_ref` de l'API

- **Fichier** : `AllureVsPenteChart.tsx` l.76, `analysis.py` l.966-978
- **Problème** : Le backend renvoie 27 points de référence lisses (`pro_ref`), mais le frontend utilise `proPace` par bin (interpolé). La courbe de référence est moins lisse qu'elle ne pourrait l'être.
- **Impact** : Courbe pro dégradée, surtout si peu de bins.
- **Correction** : Rendre la courbe pro depuis `pro_ref` au lieu de `proPace` par bin.

### 🟡 Mineurs

#### m-1 : Variable `paceMean` mal nommée

- `BinPoint.paceMean` contient en réalité la médiane pondérée (`pace_med_s_per_km`), pas une moyenne.
- Renommer en `paceMedian`.

#### m-2 : Description textuelle incorrecte

- Le footer dit "La barre verticale" mais c'est une zone/bande (Area with isRange).
- Corriger le texte.

#### m-3 : Code mort `proPaceVsGrade.ts`

- Fichier non importé par le composant chart, doublon du CSV backend.
- Supprimer ou utiliser comme fallback.

#### m-4 : Types TypeScript incomplets

- `PaceVsGradeBin` (types/api.ts) ne déclare que 6 champs sur 15 renvoyés par le backend.
- Ajouter les champs optionnels manquants.

#### m-5 : Pas d'affichage du nombre d'échantillons par bin

- `pace_n` disponible mais jamais montré dans le tooltip.
- Ajouter dans le tooltip.
