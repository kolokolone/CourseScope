## Résumé de l'analyse

La demande est cohérente, bien spécifiée et techniquement faisable sans backend. Les hooks et composants existants sont suffisants. Le principal défi est l'intégration dans le shell global sans casser les règles UI existantes (notamment le container et l'absence de header dupliqué). La spec utilisateur est volontairement auto-suffisante et détaillée, ce qui facilite le travail d'agent-dev.

Les 6 KPI du hero (Distance, Temps total, Temps en mouvement, Allure moyenne, FC moyenne, D+) sont tous disponibles via `summary.*` du `RealActivityResponse`. Les insights sont calculables côté frontend à partir des champs existants (`pacing.cardiac_drift_pct`, `splits.rows`, `garmin_summary.pause_time_s`, `zones.heart_rate`).

La contrainte "Carte sans footer technique" est déjà respectée par l'implémentation actuelle d'`ActivityMap` — aucune modification n'est nécessaire.

## Décisions de cadrage

1. Container `wide` existant (max-w-[88rem] ≈ 1408px) plutôt que container local — évite de casser les règles UI.
2. Pas de variables CSS `--cs-*` — les tokens Tailwind existants suffisent.
3. Réutilisation des composants existants sans modification.
4. Composants beta isolés dans `components/activity-beta/`.
5. Pas d'ajout à la sidebar — page beta accessible manuellement.
6. Insights calculés côté frontend — pas de nouveau endpoint.

## Ambiguités rencontrées

1. La spec mentionne `gap_mean_s_per_km` (GAP) dans `garmin_summary` — ce champ peut être absent sur des GPX purs. Géré via `formatOptionalNumber`.
2. Les champs `power.avg_w` vs `power.mean_w` — le code existant utilise les deux selon l'endroit. Le hook retourne `power.mean_w`. À documenter dans la spec.
3. Certains champs "Section A/B" dans la page actuelle ont des noms anglais ("Section E - Cadence et dynamique de course"). La demande utilisateur demande des noms français pour les accordéons.
4. La spec utilisateur mentionne un bouton menu `⋮` en haut à droite — facultatif, non prioritaire.
