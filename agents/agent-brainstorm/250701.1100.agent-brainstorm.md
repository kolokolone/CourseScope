## Résumé de l'analyse

### KPI déjà en place
- **Monotony / Strain** : déjà dans `TrainingLoadChart.tsx` (current_monotony, current_strain en KPI cards). **Aucun travail nécessaire.**

### KPI à moitié faits (backend OK, pas de frontend)
- **Session taxonomy** : endpoint `GET /progress/session-taxonomy` et hook `useProgressSessionTaxonomy()` existent. Aucun composant UI. **Travail frontend uniquement.**
- **Long run dose** : tag auto-assigné par l'indexeur, compté dans session taxonomy. Pas de visualisation dédiée. **Endpoint dédié + composant frontend.**

### KPI inexistants
- **Intensity distribution** : rien n'existe — ni backend, ni frontend. Nécessite ajout colonnes DB + endpoint + composant.
- **VAM trend** : VAM stocké par montée dans ProgressActivityClimb, pas agrégé, pas exposé en tendance. Nécessite endpoint + composant.

## Décisions de cadrage

1. **Monotony/Strain ignorés** : déjà faits.
2. **Intensity distribution = zones HR** (pas pace, pas power) : la FC est la métrique la plus universelle.
3. **Option A pour intensity** : colonnes z1-z5 ajoutées à ProgressActivityIndex (nullable, rétrocompatible).
4. **VAM max par activité** : meilleure performance de grimpe, plus parlant que VAM moyen.
5. **Pas de tagging manuel UI** : complexité trop élevée pour cette itération (P3).
6. **Pas d'onglets** : nouvelles sections dans le flux existant de la page Progression.

## Ambiguïtés rencontrées

- **Performance intensity distribution** : tranché en faveur de colonnes DB pré-calculées (Option A).
- **VAM aggregation strategy** : tranché en faveur de VAM max par activité.
- **Page overload** : tranché en faveur de l'ajout dans le flux existant sans onglets.

## Points bloquants

Aucun. Tous les KPI identifiés sont techniquement réalisables sans modification d'architecture.
