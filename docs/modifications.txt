# CourseScope — Spécification UI détaillée pour `/activities-beta/[id]`

Objectif : créer une page bêta de détail d’activité plus lisible, plus analytique et plus proche d’un tableau de bord sportif moderne, tout en conservant l’identité visuelle actuelle de CourseScope et en réutilisant les endpoints backend existants.

---

## 1. Intention générale

La nouvelle page `/activities-beta/[id]` doit être une page bêta autonome de détail d’activité. Elle doit offrir une organisation dense mais lisible : résumé de séance, indicateurs clés, analyse principale, carte, splits, zones, relief, puis détails techniques repliables.

Le haut de page attendu est un grand bloc d’en-tête propre et lisible, placé juste au-dessus des sous-catégories de navigation : `Aperçu`, `Analyse`, `Splits`, `Carte`, `Courbes`, `Relief`, `Zones`, `Détails`. Ce hero doit afficher le nom de l’activité, ses métadonnées et les KPI principaux sous forme de grandes tuiles horizontales.

La suite de page doit être organisée comme un dashboard sportif : deux cartes d’aperçu en haut, une grande analyse multi-séries, une grande carte GPS, puis des sections de détails plus compactes. La page ne doit pas ressembler à une succession d’onglets techniques isolés, mais à une fiche d’analyse continue.

La carte doit être intégrée dans une carte UI propre, mais sans les petites informations techniques sous la carte. Autrement dit, l’encadré “Carte” ne doit contenir que le titre, les contrôles de carte, la carte elle-même, la légende éventuelle et les boutons utiles. Les métriques comme `D+`, `D-`, altitude min/max, pente moyenne, pause max ne doivent pas être affichées directement sous la carte. Elles doivent être disponibles ailleurs, par exemple dans `Relief et pente` ou dans `Détails techniques`.

La page doit devenir une vraie page d’analyse sportive : elle ne doit pas seulement afficher des données, elle doit organiser les données pour que l’utilisateur comprenne rapidement ce qu’il faut retenir de l’activité.

Ce document est volontairement auto-suffisant : il ne faut pas faire référence à une maquette externe pour l’implémenter. Les agents qui travailleront sur le projet doivent pouvoir comprendre l’interface uniquement à partir de cette spécification textuelle.

---

## 1.1 Contrainte majeure : nouvelle page frontend uniquement, sans changement backend prévu

L’implémentation de `/activities-beta/[id]` doit normalement être une évolution frontend uniquement. Elle doit se servir des endpoints, hooks, clients API, types et données déjà utilisés par la page existante `/activities/[id]`.

Règle principale : ne pas modifier le backend FastAPI pour créer cette page bêta. Ne pas ajouter d’endpoint, ne pas modifier le schéma de base de données, ne pas changer les migrations, ne pas modifier la logique de parsing côté serveur et ne pas changer les contrats API existants pour cette demande UI.

La page bêta doit réutiliser la même source de données que la page actuelle. Concrètement :

- inspecter la page actuelle `/activities/[id]` ;
- identifier le hook ou client API déjà utilisé pour charger une activité ;
- réutiliser ce hook ou ce client dans `/activities-beta/[id]` ;
- réutiliser les mêmes objets `activity`, séries, splits, métriques, zones, trace GPS et champs dérivés déjà disponibles ;
- faire les transformations d’affichage côté frontend quand elles sont légères : formatage, regroupement, filtrage des valeurs absentes, calculs simples de pourcentage ou de résumé ;
- ne pas demander au backend une nouvelle forme de payload uniquement pour des raisons de présentation UI.

Si une donnée n’existe pas dans la réponse actuelle, ne pas casser l’interface et ne pas modifier le backend immédiatement. Afficher un fallback propre : `Non disponible`, `Donnée absente`, `Puissance non fournie`, `Trace GPS absente`, etc.

Exception possible, mais à traiter hors de cette tâche : si l’implémentation révèle un vrai bug backend déjà présent, ou une donnée supposée existante mais incorrecte, il faut le documenter séparément. Ne pas glisser cette correction dans la refonte UI sans validation explicite.

Cette contrainte est importante parce que `/activities-beta/[id]` est une page de test d’organisation et de rendu. Elle doit permettre de comparer la nouvelle présentation avec `/activities/[id]` sans risque de régression backend.

---

## 2. Ce qu’il faut conserver

Conserver l’identité graphique actuelle de CourseScope :

- fond général gris très clair ;
- sidebar blanche fixe à gauche ;
- cartes blanches avec bordure fine ;
- ombres très légères ;
- bleu marine comme couleur principale ;
- coins arrondis modérés ;
- typographie sobre ;
- densité d’information élevée mais contrôlée ;
- interface professionnelle, pas flashy.

Ne pas partir sur une refonte sombre, colorée ou trop “fitness app mobile”. L’objectif est un dashboard web sérieux, proche de Runalyze, Garmin Connect, Intervals.icu ou TrainingPeaks, mais dans le style CourseScope.

---

## 3. Structure globale de la page

La page doit suivre cette organisation verticale :

1. Sidebar CourseScope inchangée.
2. Zone de contenu principale centrée.
3. Ligne supérieure discrète : retour, date, menu.
4. Grand hero d’activité : titre, métadonnées et KPI principaux sous forme de tuiles horizontales.
5. Navigation horizontale sticky sous le hero.
6. Section `Aperçu` : résumé de séance + indicateurs clés.
7. Section `Analyse` : courbe principale multi-séries.
8. Section `Carte` : carte seule, sans métriques techniques sous la carte.
9. Section `Splits` + `Zones` en deux colonnes.
10. Section `Relief` pleine largeur.
11. Sections repliables : détails techniques, prédictions, puissance maximale, highlights.

Le rendu desktop doit ressembler à une grande fiche d’activité lisible en un seul flux vertical, sans imposer des clics constants entre onglets.

## 6. Hero d’activité — grand en-tête clair au-dessus de la navigation

Le hero est le bloc principal au-dessus des sous-catégories. Il doit être plus visuel et plus clair que l’actuel bandeau compact, avec une structure de fiche d’activité : titre fort, badges de contexte, actions discrètes, puis grands KPI.

### 6.1 Structure

Le hero doit contenir :

1. Ligne titre :
   - nom de l’activité : `Paris · Z2 · récup` ;
   - icône crayon pour renommer ;
   - bouton `Exporter` optionnel ;
   - étoile ou menu optionnel.

2. Ligne métadonnées :
   - date et heure ;
   - source : `Garmin Forerunner 965`, `Garmin`, `FIT`, `GPX`, selon données disponibles ;
   - type : `Course à pied` ;
   - badge d’intention : `Z2 · Recovery`, `Endurance`, `Seuil`, etc. uniquement si détecté proprement.

3. Ligne KPI principaux sous forme de grandes cartes horizontales :
   - Distance ;
   - Temps total ;
   - Temps en mouvement ;
   - Allure moyenne ;
   - FC moyenne ;
   - Dénivelé positif.

Ne pas surcharger le hero avec toutes les métriques. Le hero doit donner le contexte immédiat.

Cette carte doit présenter des insights interprétables, pas seulement des chiffres.

## 10. Section Analyse principale

Cette section correspond au grand graphe multi-séries central de la page.

### 10.1 But

L’utilisateur doit comprendre la séance en un coup d’œil : allure, fréquence cardiaque, altitude, pente, cadence et puissance doivent être lisibles ensemble.

### 10.2 Contenu

Carte pleine largeur :

- titre : `Analyse principale` ;
- contrôles :
  - X-axis : `Distance` / `Temps` ;
  - lissage : `Off`, `5s`, `10s`, `15s`, `20s`, `30s` ;
  - bouton `Personnaliser les séries` optionnel.
- graphe principal ;
- tooltip synchronisé ;
- légende claire.

### 10.3 Séries à afficher

Par défaut :

- Allure : bleu ;
- FC : rouge ;
- Altitude : vert ;
- Pente : orange ;
- Cadence : jaune ;
- Puissance : violet/rose si disponible.

Si puissance ou cadence absente : ne pas afficher la série, ne pas afficher une courbe plate à zéro.

### 10.4 Tooltip attendu

Tooltip au survol :

```text
11.2 km
1:05:12
Allure      05:32/km
FC          152 bpm
Altitude    54 m
Pente       -1.2 %
Cadence     82 spm
Puissance   428 W
```

Le tooltip doit être sombre, compact et lisible.

### 10.5 Style du graphe

Le graphe doit avoir une hauteur confortable :

```css
.main-analysis-chart {
  height: 420px;
}

@media (max-width: 900px) {
  .main-analysis-chart {
    height: 360px;
  }
}
```

Utiliser `ResponsiveContainer` si Recharts est déjà utilisé.

### 10.6 Recharts — exemple indicatif

```tsx
<ResponsiveContainer width="100%" height={420}>
  <ComposedChart data={chartData} margin={{ top: 16, right: 24, bottom: 8, left: 8 }}>
    <CartesianGrid strokeDasharray="3 3" stroke="#e2e8f0" />

      tickFormatter={formatPace}
      reversed
      tick={{ fontSize: 12, fill: '#2563eb' }}
    />
    <YAxis
      yAxisId="hr"
      orientation="right"
      tick={{ fontSize: 12, fill: '#ef4444' }}
    />
    <Tooltip content={<ActivityTooltip />} />
    <Legend />
    <Line yAxisId="pace" type="monotone" dataKey="pace" stroke="#2563eb" dot={false} strokeWidth={2} />
    <Line yAxisId="hr" type="monotone" dataKey="heartRate" stroke="#ef4444" dot={false} strokeWidth={2} />
```

1. panels empilés synchronisés ;
2. séries normalisées visuellement avec tooltip en valeurs réelles.

La solution la plus propre : panels synchronisés si le composant actuel le permet. Sinon, courbes normalisées mais avec axe secondaire clair.

## 11. Section Carte — sans informations techniques sous la carte

Cette section doit afficher une grande carte GPS interactive et appliquer la demande spécifique : ne pas afficher les petites métriques techniques sous la carte.

### 11.1 Contenu autorisé dans l’encadré Carte

Dans la carte UI :

- titre `Carte` ;
- sous-titre court : `Trace GPS colorée selon l’allure, la FC ou la pente.` ;
- contrôle `Colorer par` : `Allure`, `FC`, `Pente`, `Puissance` si disponible ;
- bouton recentrer ;
- bouton plein écran ;
- carte Leaflet ;
- légende compacte intégrée à la carte ;
- marqueurs km si disponible ;
- marqueurs pauses si disponible.

### 11.2 Contenu interdit sous la carte dans cette section

Ne pas afficher sous la carte :

- `D+` ;
- `D-` ;
- `Altitude min` ;
- `Altitude max` ;
- `Pente moyenne` ;
- `Pause max` ;
- `Nombre de pauses` ;
- autres mini KPI techniques.

Ces données doivent être déplacées vers :

- `Relief et pente` ;
- `Détails techniques` ;
- éventuellement le hero si la donnée est majeure.

### 11.3 Layout de la carte

La carte doit être large. Hauteur recommandée :

```css
.activity-map-container {
  height: 460px;
  border-radius: 14px;
  overflow: hidden;
  border: 1px solid #dbe3ef;
}

@media (max-width: 900px) {
  .activity-map-container {
    height: 360px;
  }
}
```

### 11.4 Exemple de structure

```tsx
<Card id="carte" className="scroll-mt-24">
  <CardHeader>
    <div>
      <CardTitle>Carte</CardTitle>
```

## 16. États vides et qualité des données

La page bêta doit être robuste. Ne jamais afficher :

- `undefined` ;
- `null` ;
- `NaN` ;
- `Infinity` ;
- `—` partout dans une grande table ;
- graphe vide ;
- courbe plate à zéro pour une donnée absente.

Messages attendus :

- `Donnée non disponible dans ce fichier.`
- `Puissance non fournie pour cette activité.`
- `Cadence non disponible.`
- `Trace GPS absente.`
- `Aucune pause détectée.`
- `Aucune montée significative détectée.`

Créer un helper central :

```ts
export function isValidNumber(value: unknown): value is number {
  return typeof value === 'number' && Number.isFinite(value);
}

export function formatOptionalNumber(
  value: unknown,
  formatter: (n: number) => string,
  fallback = 'Non disponible'
): string {
  return isValidNumber(value) ? formatter(value) : fallback;
}
```

## 22. Points d’attention importants

### 22.1 Ne pas confondre page bêta et page existante

La page existante `/activities/[id]` ne doit pas être cassée. La nouvelle organisation doit être testée dans :

```text
/activities-beta/[id]
```

Cela permet de comparer les deux pages avant migration.

### 22.2 Ne pas modifier le backend pour cette refonte UI

Cette page bêta doit consommer les mêmes données que la page actuelle. L’objectif est de tester une nouvelle organisation visuelle, pas de changer les contrats serveur.

À ne pas faire dans cette tâche :

- créer un nouveau endpoint FastAPI ;
- modifier un endpoint existant ;
- modifier les modèles backend ;
- ajouter une migration de base de données ;
- changer le parsing FIT/GPX ;
- changer la structure de réponse API pour faciliter uniquement le rendu de la page bêta.

À faire :

- réutiliser le hook existant de chargement d’activité ;
- réutiliser les composants existants quand ils sont fiables ;
- créer des composants frontend bêta qui transforment les données existantes en blocs visuels plus lisibles ;
- afficher des fallbacks propres si certaines données ne sont pas disponibles.

### 22.3 Réutiliser les composants existants

Ne pas réécrire inutilement les gros composants si des composants fiables existent déjà. Réutiliser :

- la logique de récupération d’activité ;
- les formateurs existants ;
- les composants de courbes existants si propres ;
- `ActivityMap` si robuste ;
- `MetricsRegistryRenderer` pour les détails techniques.

Créer des wrappers bêta si nécessaire pour réorganiser l’UI.

### 22.4 Éviter la surinterprétation

Les insights automatiques doivent rester prudents. Exemple :

Correct :

```text
Sortie probablement orientée endurance facile, car la majorité du temps semble passée en zones basses.
```

À éviter :

```text
Séance parfaite de récupération, aucun problème.
```

### 22.5 Faire disparaître les gros blocs pauvres

Les cartes contenant une ou deux lignes faibles doivent être fusionnées ou repliées. L’espace vertical est précieux.

## 23. Critères d’acceptation

La nouvelle page est considérée satisfaisante si :

- `/activities-beta/[id]` existe et fonctionne ;
- l’ancienne page `/activities/[id]` continue de fonctionner ;
- aucun changement backend n’est nécessaire pour cette page bêta ;
- les endpoints existants, hooks existants et contrats API existants sont réutilisés ;
- le haut de page affiche un hero clair avec titre, métadonnées et KPI principaux ;
- la suite adopte une organisation dense, claire et exploitable ;
- la navigation `Aperçu / Analyse / Splits / Carte / Courbes / Relief / Zones / Détails` est placée sous le hero ;
- la carte n’affiche plus les petites métriques techniques sous elle ;
- les métriques techniques restent accessibles ailleurs ;

- aucun label anglais inutile ne reste dans la page ;
- les données absentes sont gérées proprement ;
- les graphes ne cassent pas si puissance, cadence ou GPS manquent ;
- le rendu est lisible sur desktop, laptop et mobile ;
- `npm run build` passe côté frontend.
