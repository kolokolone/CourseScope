## 1) Deploiement Docker + reseau local (Dockge) - IMAGE UNIQUE (API + WEB dans 1 conteneur)

Objectif: une seule image Docker a pull, ex: `ghcr.io/kolokolone/coursescope:main`, qui lance automatiquement:
- backend FastAPI (uvicorn) sur `127.0.0.1:8000` (interne au conteneur)
- frontend Next.js sur `0.0.0.0:3000` (expose au LAN)

Le navigateur des clients LAN parle UNIQUEMENT au frontend (port 3000). Les appels API passent par le proxy Next `/api/*` -> `http://127.0.0.1:8000/*` dans le meme conteneur.

### 1.1 Contexte (Windows local vs Docker)

Local Windows (actuel):
- tu lances `start_backend.bat` puis `start_frontend.bat`.
- le frontend en dev utilise `/api` (proxy Next) et le backend est sur 127.0.0.1:8000.

Docker (cible):
- tu lances 1 seul conteneur.
- le conteneur lance backend + frontend automatiquement, comme une stack "immich-like" mais dans un conteneur unique.

### 1.2 Pourquoi ce choix (et les compromis)

Avantages:
- 1 seule image a publier/pull.
- 1 seul service compose dans Dockge.
- Pas de CORS en production (proxy Next, meme origin cote navigateur).

Compromis:
- Image plus lourde (Node + Python + deps).
- Deux processus dans un conteneur => il faut un lanceur robuste (gestion SIGTERM, arret propre, restart, multi-thread s'il le faut).

### 1.3 Ce qui bloque le LAN/Docker aujourd'hui (a corriger)

1) `frontend/.env.local` force des appels directs vers localhost
- Fichier: `frontend/.env.local`
- Constat: `NEXT_PUBLIC_API_URL=http://localhost:8000`
- Probleme en prod/LAN: le navigateur d'un client LAN va appeler SON `localhost:8000` (KO) et ca contourne le proxy `/api`.
- Fix requis: retirer `frontend/.env.local` du repo (remplacer par un exemple) et ne pas definir `NEXT_PUBLIC_API_URL` en production Docker.

2) Script Linux existant `run_linux.sh` est "dev only"
- Fichier: `run_linux.sh`
- Constat:
  - cree une venv
  - fait `pip install -r requirements.txt`
  - lance `uvicorn --reload --host 0.0.0.0`
  - lance `npm run dev`
- Pour Docker (prod), il faut:
  - ne pas installer au runtime (tout doit etre baked dans l'image)
  - lancer uvicorn sans reload
  - lancer `next start` (pas `next dev`)
  - binder l'API sur 127.0.0.1 (non expose)
  - binder le web sur 0.0.0.0 (expose)

3) CORS backend (non bloquant en prod avec proxy)
- Fichier: `backend/api/main.py`
- Etat actuel: CORS limite a localhost/127.0.0.1.
- En prod avec image unique (API non exposee), c'est OK.
- Option: ajouter `COURSESCOPE_CORS_ORIGINS` (CSV) uniquement si tu decides d'exposer l'API (port 8000) au LAN.

### 1.4 Strategie recommandee: reutiliser `run_linux.sh` comme lanceur (avec un mode "docker/prod")

But: garder 1 seul point d'entree cross-platform:
- Windows local: `start_backend.bat` + `start_frontend.bat` (inchanges)
- Linux dev: `./run_linux.sh` (inchanges)
- Docker prod: `./run_linux.sh --docker` (nouveau mode)

Changement a implementer dans `run_linux.sh`:

1) Ajouter un mode "docker/prod" (flag ou env)
- Exemple: `./run_linux.sh --docker`
- Ou: `COURSESCOPE_MODE=docker ./run_linux.sh`

2) En mode docker:
- Ne pas creer de venv
- Ne pas faire `pip install`
- Ne pas faire `npm install`/`npm ci`
- Lancer backend en background:
  - `python3 -m uvicorn backend.api.main:app --host 127.0.0.1 --port 8000`
- Optionnel: attendre que `http://127.0.0.1:8000/health` reponde 200 (poll via python)
- Lancer frontend en foreground:
  - `cd frontend && npm run start -- -H 0.0.0.0 -p 3000`
- Garder un `trap` pour tuer le backend quand le script se termine.

3) Gestion signaux (important en conteneur)
- Le script doit terminer proprement sur SIGTERM (Dockge/Compose stop).
- Recommandation: installer `tini` et l'utiliser comme entrypoint pour une gestion propre des signaux.

### 1.5 Variables d'environnement (contrats)

#### 1.8.2 `Dockerfile` (racine)

Remarques:
- Ce Dockerfile suppose que `run_linux.sh` supporte `--docker`.
- Attention Windows/CRLF: `run_linux.sh` doit etre executable ET en LF. Sinon, le shebang peut casser en Linux. Recommandation: corriger au build via `sed`.

```dockerfile
# syntax=docker/dockerfile:1

FROM node:20-bookworm-slim AS web-build
WORKDIR /app/frontend

COPY frontend/package.json frontend/package-lock.json ./
RUN npm ci

COPY frontend ./
RUN npm run build


FROM node:20-bookworm-slim

WORKDIR /app

ENV NODE_ENV=production \
    COURSESCOPE_DATA_DIR=/data

RUN apt-get update \
  && apt-get install -y --no-install-recommends \
    python3 python3-pip \
    tini \
  && rm -rf /var/lib/apt/lists/*

COPY requirements.txt ./
RUN pip3 install --no-cache-dir -r requirements.txt

COPY backend ./backend

# Frontend runtime (includes node_modules + .next)
COPY --from=web-build /app/frontend /app/frontend

COPY run_linux.sh /app/run_linux.sh

# Remove CRLF if the repo was edited on Windows
RUN sed -i 's/\r$//' /app/run_linux.sh \
  && chmod +x /app/run_linux.sh

EXPOSE 3000

ENTRYPOINT ["/usr/bin/tini", "--"]
CMD ["/app/run_linux.sh", "--docker"]
```

### 1.9 Workflow GitHub Actions (GHCR) - une seule image

Fichier: `.github/workflows/docker-image.yml`

But:
- construire et publier `ghcr.io/kolokolone/coursescope:main`.
- sur PR: build only (pas de push).

Workflow minimal:
```yaml
name: Docker Image (GHCR)

on:
  push:
    branches: ["main"]
  pull_request:
    branches: ["main"]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: coursescope

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Login to GHCR
        if: github.event_name != 'pull_request'
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: .
          push: ${{ github.event_name != 'pull_request' }}
          tags: |
            ${{ env.REGISTRY }}/${{ github.repository_owner }}/${{ env.IMAGE_NAME }}:main
            ${{ env.REGISTRY }}/${{ github.repository_owner }}/${{ env.IMAGE_NAME }}:sha-${{ github.sha }}
```

### 1.10 Deploiement Dockge (marche a suivre)

GHCR + pull
1) Ajouter `Dockerfile`, `.dockerignore`, modifier `run_linux.sh`, retirer `frontend/.env.local`.
2) Ajouter `.github/workflows/docker-image.yml`.
3) Push sur `main` => GitHub Actions publie l'image.
4) Sur le serveur: `docker login ghcr.io -u <ton_user>` (PAT scope `read:packages` si package prive).
5) Dans Dockge: stack `coursescope` avec `compose.yaml` (image:) -> `Pull` -> `Up`.
6) Acces: `http://<ip_du_serveur>:3000`
